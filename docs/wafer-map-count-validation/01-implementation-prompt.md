# RAD 웨이퍼맵 수량 검증 구현 프롬프트

## 작업 목적

로컬 `D:\Source\CDT-320_New`의 현재 `master`에서 RAD 형식 웨이퍼맵 수량 검증을 수정한다. 분석 결과에 따른 구현 승인을 받은 범위이며, 원격에서 받은 RKE용 YZAMH 웨이퍼맵이 실제 레코드 수와 일치하는 `%` 헤더로 검증되도록 한다. 맵 좌표와 BIN별 작업 대상은 파일의 `X= ... Y= ... B= ...` 레코드를 기준으로 생성한다.

YZAMH `.02`~`.17`은 모두 `%730`, `&0732`, 실제 레코드 730개, 고유 XY 730개다. 기존 코드가 `&0732`를 실제 레코드 수로 요구하면 정상적인 이 파일군을 거부한다. 이 작업은 수량 차이를 무시하는 우회가 아니라 각 헤더와 실제 레코드의 역할을 분리하는 변경이다.

## 기준 저장소와 작업 제한

1. 저장소 루트, 브랜치, 변경 상태를 먼저 확인한다. 구현 시작 시 확인된 상태는 `master`, `origin/master`보다 97커밋 앞섬, 기존 변경 없음이다. 실제 실행 시 재확인한다.
2. `AGENTS.md`를 따른다. 현재 `master`에서 작업하고 별도 요청 없이 브랜치 전환, 커밋, 푸시를 하지 않는다.
3. 운영 데이터와 원격 원본을 수정하지 않는다. `D:\CDT-320`은 배포 영역이며 소스 루트나 빌드 출력으로 사용하지 않는다.
4. 장비 구동, 축 이동, IO 출력, 자동 운전, 실제 카메라·원격 서버 연결은 수행하지 않는다.

## 구현 요구사항

### 수량과 헤더 검증

- RAD 레코드 전체를 읽어 실제 레코드 수와 고유 XY 수를 계산한다. BIN 필터 적용 전의 전체 레코드를 검증한다.
- `%` 수량은 필수이며 유효한 양의 정수여야 한다. 실제 레코드 수와 같아야 한다. 중복 XY가 없어 실제 수와 고유 XY 수도 같아야 한다.
- `&` 수량도 별도 헤더 값으로 읽고 유효한 양의 정수인지 검사한다. `%`와 같은 변수에 덮어쓰지 않는다.
- `%` 또는 `&`의 누락, 0, 음수, 잘못된 숫자, 표현 범위를 벗어난 숫자, 중복 헤더 토큰, 충돌하는 헤더 값은 실패로 처리한다. 같은 값이 반복되어도 중복 토큰은 허용하지 않는다.
- 수량 토큰은 닫는 `/`까지 완결된 형식이어야 한다. 첫 30행에서 멈추지 않고 레코드 시작 전 전체 헤더를 검사하여 뒤쪽 중복·충돌도 거부한다.
- 수량 토큰은 해당 RAD 헤더에서 검사한다. 뒤에 이어지는 검사 항목명·스펙·수치 데이터의 `%` 등 문자를 헤더 수량으로 오인하지 않는다.
- `%`와 실제 레코드 수가 다르거나, 레코드가 0개거나, XY가 중복되거나, `X=`로 시작하는 레코드가 올바르게 해석되지 않으면 실패로 처리한다. 불완전한 레코드를 건너뛰어 수량을 맞추지 않는다.
- 정상적인 X/Y/B 레코드 뒤에 붙는 `D=`, `S=`, `Z=`, `C=`, `RD=` 등 기존 추가 필드는 허용한다. `YZ8XRD.07`과 같은 후행 필드 형식을 잘못된 레코드로 판정하지 않는다.
- `E= EOW`는 종료 표식이며 Die 레코드 수에 포함하지 않는다.

### `%`와 `&`가 다른 정상 파일

- `% = 실제 레코드 수 = 고유 XY 수`이고 파서 내부의 레코드·중복·맵 정규화 검증이 모두 성공했다면, `&`가 다르다는 이유만으로 실패시키지 않는다.
- 유효한 맵으로 검증된 뒤 파일명, `%`, `&`, 실제 레코드 수가 포함된 한국어 경고 로그를 남기고 기존 맵 생성 흐름을 계속한다.
- 파서 내부 검증 도중 다른 오류가 발생한 파일에는 정상 진행을 뜻하는 불일치 경고를 먼저 남기지 않는다. 원격 서비스의 피치·선택 BIN 등 후속 검증은 기존 흐름을 유지하며 파서 성공만으로 장비 진행을 확정하지 않는다.
- `% = & = 실제 레코드 수`이면 이 수량 불일치 경고를 남기지 않는다.

### 보존과 변경 범위

- `%`와 `&`는 내부 전용 헤더 구조에서 별도로 관리한다. 원본 캐시 파일을 그대로 보존하고 불일치 로그로 두 값을 추적한다.
- 저장 JSON 스키마와 기존 직렬화 키는 확장하거나 변경하지 않는다. 기존 수량 메타데이터가 필요하면 검증을 통과한 `%` 값을 사용한다.
- 기존 좌표 변환, 축 방향, 피치 해석, BIN 해석, 픽업 순서, 다운로드·바코드·LOT 흐름, 레시피 승인 절차를 변경하지 않는다.
- Camtek 및 PLACE GRID 형식의 기존 판별·파싱 동작을 유지한다.
- `UseLotNetworkWaferMap`, 네트워크 포맷, 레시피, Teaching 등 운영 설정을 변경하지 않는다.

## 검증 요구사항

1. 기존 RAD 회귀 파일 6개를 현재 검증 도구의 기준대로 검사하고 구체적인 파일과 기대 결과를 기록한다.
2. `D:\Source\EQP_Handler\20260907\YZAMH\YZAMH.02`부터 `.17`까지 16개 모두 검사한다. 각 파일의 `%730`, `&732`, 실제 레코드 730개, 고유 XY 730개를 확인한다. BIN 1의 합계는 8,021개여야 한다. 원본 XY와 양수 BIN이 보존되고, 비양수 BIN은 기존 non-target / BinCode 255 정규화가 유지되는지도 확인한다.
3. `D:\CDT-320\Config\WaferMap\YZ8XRD.07`의 X/Y/B 뒤 추가 필드 1,257개가 정상 처리되는지 확인한다.
4. 격리된 합성 입력으로 헤더 누락·0·잘못된 숫자·중복·충돌, `%` 수량 불일치, XY 중복, 잘못된 X= 레코드, 0개 레코드, 정상 후행 필드 및 `%`/`&` 차이 경고 시점을 확인한다.
5. Camtek 및 PLACE GRID의 기존 경로를 검증한다.
6. 검증에 사용한 원본 파일의 SHA256을 전후 비교한다. 합성 입력과 빌드 출력은 별도 검증 경로에만 만든다.
7. `git diff --check`, 관련 정적 검사, 별도 `OutDir`를 지정한 `/t:Build`를 수행한다. 원본 저장소에서 Clean/Rebuild는 실행하지 않는다.
8. 실제 원격 통신, `.02`/`.03`의 현장 정렬, 실픽업은 미수행 항목으로 남긴다. 정적 검사·격리 실행·컴파일 성공을 장비 운전 검증 성공으로 표현하지 않는다.
