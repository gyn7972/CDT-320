# 비전 확인 방식 NG 라우팅 구현 지시 프롬프트 (2026-08-21 확정)

## 0. 방식 확정 배경

NG 다이 작업자 확인을 **비전 PC 쪽 UI**에서 수행하고, 핸들러는 최종 RESULT(OK/NG)를
길게 기다렸다가 받은 대로 Good/NG Stage에 배치만 한다. (사용자 확정 2026-08-21)
- 핸들러 다이얼로그 안(`NG확인다이얼로그_구현지시_프롬프트_2026-08-21.md`)은 **대안으로 보관** — 비전 수정 불가 시 사용.
- 비전 PC 수정은 별도 진행(사용자 담당). 본 문서 §5가 비전 쪽에 전달할 합의사항.

## 1. 동작 개요 (확정 사양)

| 항목 | 내용 |
|---|---|
| 비전 동작 | PASS는 즉시 RESULT 송신(기존과 동일). **NG만 RESULT 보류** → 작업자가 비전 PC에서 확인/오버라이드 → 확정 RESULT 송신 |
| 핸들러 대기 | 최종 RESULT 대기 타임아웃을 12초 → **설정값(기본 120초)** 로 분리 확대 (사용자 확정 2026-08-25: AppSettings + General 설정 페이지 노출). **RouteByInspectionResult 모드에서만** — ForceGoodStage 로트는 기존 12초 유지(회귀 방지). 모드는 검사 시퀀스 시작 시 1회 조회·고정(스냅샷 원칙) |
| 작업자 호출 | 게이트 대기 10초 경과 시부터 **10초마다 부저 1회(짧게) + 경광등 녹+황** (사용자 확정 2026-08-25 — 작업자가 비전 이미지 보고 판정하도록 호출), RESULT 수신 시 복원 |
| 무응답(타임아웃 초과) | 기존 알람 경로 그대로 정지 — Bottom: `PICKER-PLACE-BOTTOM-RESULT-MISSING`, Side: `PICKER-PLACE-INSPECTION-RESULT-MISSING` (**만료=알람 통일 이미 되어 있음**, 코드 확인 2026-08-21) |
| CYCLE STOP 중 보류 | **즉시 깨워서 안전 정지** (사용자 확정 2026-08-25). 게이트 대기를 `Context.CreateCycleStopLinkedSource(ct)`로 감싸되 **RouteByInspectionResult 모드에서만** 적용(ForceGoodStage 정지/drain 동작 무변경). 안전 근거: 재개 로직이 판정 미확정 보유 다이를 **무조건 Bottom 검사부터 재개**(PickerProcessSequence.cs:870-876, :797 Place 재개는 전원 판정 확정일 때만) → 재검사→비전 재보류→작업자 확인으로 자연 복구, 수동 복구 불필요 |
| GOOD 오버라이드 | 비전이 verdict 토큰을 PASS로 송신하면 끝. 핸들러 오버라이드 코드 불필요 |
| 이력 | 비전이 RESULT에 `operator_override=1` 필드 추가 → 핸들러 `AppendVisionRawMeasurements`가 raw 전체를 검사기록·CSV에 **자동 저장** (핸들러 코드 무변경) |
| 택트 | Good 다이 지연 0 (비전이 PASS 즉시 송신), NG 다이만 작업자 응답 대기 |

## 3. 안전 근거 (분석 완료 2026-08-21)

- Bottom은 MRESULT/최종 RESULT가 이미 2메시지 분리 — MRESULT(축 진행 게이트)는 즉시 오고, 최종 RESULT는 지금도 백그라운드 수집 후 Place 게이트에서 소비. Side도 EPD 후 픽커는 진행, RESULT는 게이트 소비. **보류 대기 중 축은 게이트에서 정지 상태.**
- 게이트는 lease 획득 전 → **보류 중 반대편 픽커 Place 정상 진행.**
- 라우팅 게이트(`WaitInspectionResultsBeforePlaceDownAsync`)는 `ResolveOutputSide` 전에 통과 필수 → 받은 verdict 그대로 Good/NG 분기(기존 검증 경로 무변경).
- 타임아웃 만료는 Bottom/Side 모두 기존 알람 정지 경로 — 추가 작업 불필요.

## 5. 비전 PC 합의사항 (비전 개발 측 전달용 — 재점검·보강 2026-08-25)

### 5-1. 대상 메시지 정의 (핸들러 프로토콜 실체 기준)
| 메시지 | 카메라/프로파일 | 보류 가능? |
|---|---|---|
| ACK, EPD | 전체 | **금지 — 즉시 송신** (핸들러 축 진행 게이트) |
| **MRESULT** (Bottom 중간 결과, STATUS=OK 필수) | CAMERA=`BOTTOM`, profile=`BOTTOM_SURFACE` | **금지 — 즉시 송신** (Side 접근 위치 계산에 사용) |
| 최종 RESULT (Bottom 판정) | CAMERA=`BOTTOM`, profile=`BOTTOM_SURFACE` | **판정 FAIL일 때만 보류 가능** |
| 최종 RESULT (Side 판정, 0°/90° 통합 1건) | CAMERA=`FRONTSIDE`/`REARSIDE`, profile=`SIDE_JUDGE` | **판정 FAIL일 때만 보류 가능** |

- 판정 PASS(OK)는 어떤 경우에도 즉시 송신 — Good 다이 택트 무영향의 전제.
- Bottom FAIL·Side FAIL은 각각 독립 보류(같은 다이에 확인 2건 가능). 확인 UI 구성은 비전 자유.

### 5-2. 보류 기능 활성화 방법 (※ 재점검에서 발견된 공백 — 확정 필요)
핸들러는 INSPECT 요청에 라우팅 모드를 실어 보내지 않으므로 **비전은 핸들러 레시피 모드를 알 수 없다.**
→ **비전 프로그램에 보류(작업자 확인) ON/OFF 설정을 두고, NG 라우팅 로트 운전 시에만 ON**으로 운용한다(운영 규칙).
- ForceGoodStage 로트에서 ON이면 핸들러가 12초 만에 RESULT-MISSING 알람 → 즉시 원인 파악 가능(위험하지는 않음).
- (대안: 핸들러 INSPECT 요청에 모드 필드 추가 — 핸들러/비전 양쪽 프로토콜 수정 필요라 1차 제외. 필요 시 2차.)

### 5-3. 보류 중 운영 규칙
1. **보류 상한**: 핸들러 설정값(기본 120초, General 설정) 미만으로 응답. 초과 시 핸들러가 알람 정지하며 이것이 정상 동작 — **비전이 대신 자동 송신(auto-NG 등)하지 말 것.** UI에 경과/남은 시간 표시 권장.
2. **취소 신호 없음**: 핸들러는 정지/알람 시 비전으로 아무 메시지도 보내지 않는다(핸들러 내부 정리만 수행 — VisionAdapters.AbandonPendingInspection 확인 2026-08-25). 비전은 보류 세션을 스스로 관리해야 한다.
3. **보류 폐기 규칙**: 같은 픽커/카메라로 **새 INSPECT 요청이 수신되면 이전 보류 세션은 즉시 폐기**하고 새 요청 기준으로 처리한다. 폐기된 보류의 RESULT는 **절대 늦게 송신하지 않는다** (핸들러 정지→재시작 시 보유 다이를 Bottom부터 재검사하므로 같은 die_id가 새 request_id로 다시 온다 — 이전 request_id로 송신 시 상관관계 불일치).

### 5-4. 오버라이드 송신 규칙
- 작업자 GOOD 선택 → **verdict 토큰만 `PASS`로** 바꿔 송신.
- **개별 측정값/플래그는 원본 유지** — 특히 `measure_valid`, `bottom_item_offset_x/y`, `bottom_item_offset_x/y_pass`는 절대 조작 금지 (핸들러 Place 보정 유효성 검증 :3316-3346이 참조 — 측정 무효면 오버라이드해도 알람 차단이 정상이며 그래야 안전).
- 이력 필드 추가: `operator_override=1`, `operator_decision=GOOD|NG` (미조작 다이는 필드 생략). 핸들러 검증기는 미정의 키를 거부하지 않음(확인 2026-08-25) → 자동으로 검사기록·CSV에 저장됨.
- **상관관계 필드 원본 유지**: request_id / group_id / die_id / die_index — 핸들러가 다이 일치를 검증하므로 보류 후 송신에도 그대로.
