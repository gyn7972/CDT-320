## 1. 배경

### 1-1. 요구 사항

작업 정보 > INPUT CASSETTE 페이지(ACTION 패널: LIFT WAFER MAPPING / LOADING /
UNLOADING / STOP)에는 카세트 교체 후 데이터를 초기화하는 버튼이 없다.
OUTPUT CASSETTE 페이지의 **GOOD CST CLEAR와 동일한 기능**의 버튼을 INPUT 페이지에
추가한다: 물리 카세트 교체 후 이 버튼으로 Material Data를 초기화하면, 다음 START에서
매핑부터 다시 진행된다.

### 1-2. 참조 구현 — Output GOOD CST CLEAR (그대로 미러할 것)

`QMC.CDT-320\Ui\Pages\WorkInfo\OutputCassettePage.cs`
- 배선: `btnCstClear.Click += (s, e) => CompleteCassetteExchange(BinSide.Good);` (67행)
- 본체: `CompleteCassetteExchange` (707~769행). 흐름:
  1. `CanChangeOutputCassetteData` — 컨트롤러 상태 가드(Auto/Manual/초기화/Ready 시퀀스
     완전 정지 + `_manualSequenceRunning`/`IsManualBusy`/`IsSequenceRunning` 확인, 279~310행)
  2. `CanClearOutputCassetteSideData` — 진행 중 자재 가드(스테이지·피더 보유 시 차단)
  3. 확인 다이얼로그 → **가드 재확인**(확인 중 상태 변화 방어) → 서비스 Clear →
     `TryFlushPendingSave` → 재준비 요청 → `RefreshData()` → 완료 안내
- 버튼 Enable 관리: `btnCstClear.Enabled = enabled;` (274행 — 다른 ACTION 버튼과 동일 경로)

### 1-3. 인풋 측 기존 자산 (조사 확정 — 재사용할 것)

- `MaterialStateService.ClearInputCassetteAllSlotData(out reason)`
  (`Equipment\Materials\MaterialStateService.Clear.cs:1183`) — Input1+Input2 전체 초기화.
  - 사전검사(`TryValidateCassetteRoleForClearNoLock`) 포함, 차단 시 사유 반환.
  - 초기화 시 카세트의 `IsMapped=false`, `IsPresent=false`, `CassetteLotId=""` 리셋
    (1285~1295행) → **다음 Auto START에서 매핑이 자동으로 재수행된다.**
    Output의 `RequestOutputFullPreparation` 같은 별도 요청 API는 인풋에 없다 —
    **새로 만들지 말 것.** (§5-3에서 재매핑 동작을 확인만 한다. 안 되면 보고.)
- 같은 페이지 MATERIAL 패널의 DATA ALL CLEAR 핸들러
  (`InputCassettePage.cs` `MaterialDetailView_ClearAllDataRequested`, 1068~1111행)가
  "초기화 차단"과 "저장 실패"를 구분 표시하는 확정 정책(2026-08-17)을 이미 구현했다 —
  **메시지 분기 패턴을 그대로 따를 것.**

## 2. 변경 범위 (2파일)

### 2-1. `Ui\Pages\WorkInfo\InputCassettePage.Designer.cs` — 버튼 추가

- ACTION 패널에 버튼 1개 추가: 이름 `btnCstClear`, 표기 **"CST CLEAR"**,
  ACTION 라벨/스타일은 기존 ACTION 버튼(LIFT WAFER UNLOADING 등)과 동일 컨벤션.
  배치는 STOP 버튼을 침범하지 않는 빈 자리(LIFT WAFER MAPPING 옆 빈 칸 권장 —
  기존 레이아웃 좌표를 깨지 말 것).

### 2-2. `Ui\Pages\WorkInfo\InputCassettePage.cs` — 핸들러 + 가드

1. **배선**: 생성자/초기화부의 기존 버튼 배선 위치에
   `btnCstClear.Click += (s, e) => CompleteInputCassetteExchange();` 추가.
2. **Enable 관리**: 다른 ACTION 버튼의 Enabled를 갱신하는 기존 경로(수동 시퀀스 실행
   중 비활성화 등)에 `btnCstClear`를 같이 넣는다 — Output 274행 컨벤션 미러.
3. **컨트롤러 상태 가드** `CanChangeInputCassetteData(Form1 host, string actionName)`
   신설: Output `CanChangeOutputCassetteData`(279~310행)를 그대로 미러
   (인풋 페이지의 수동 시퀀스 실행 플래그 + `IsManualBusy`/`IsSequenceRunning`/
   `IsReadySequenceRunning`/`Status` 검사, 동일 문구 스타일).
4. **진행 중 자재 가드** `CanClearInputCassetteData()` 신설 — 다음 위치에 웨이퍼가
   있으면 차단하고 사유 안내(Output `CanPrepareOutputCassetteExchange`/
   `CanClearOutputCassetteSideData` 미러):
   - `MaterialLocationKind.InputFeeder` — "InputFeeder에 진행 중인 Wafer가 있어 …
     원래 카세트로 반납/제거 후 다시 시도"
   - `MaterialLocationKind.InputStage` — "InputStage에 진행 중인 Wafer가 있어 …"
   (그 외 심층 정합성은 서비스 사전검사가 담당 — 페이지에서 중복 구현 금지.)
5. **본체** `CompleteInputCassetteExchange()`:
   1. 상태 가드 → 자재 가드
   2. 확인 다이얼로그: "INPUT 카세트(1단/2단 전체)의 Material Data만 초기화합니다.
      (OUTPUT 카세트 데이터는 유지됩니다) 진행할까요?"
   3. **가드 재확인**(Output 723~726행 미러)
   4. `MaterialStateService.ClearInputCassetteAllSlotData(out clearReason)` 호출 —
      실패 시 §1-3 확정 정책대로 "차단(저장 파일 무변경)+사유" 표시 후 종료
   5. `MaterialStateService.TryFlushPendingSave("InputCassetteCstClear")` — 실패 시
      "메모리 초기화됨/저장 파일 갱신 실패, 재시작 금지·로그 확인" 안내(Output 737~741행 미러)
   6. 화면 갱신(기존 `RefreshSelectedMaterialDetail()` + `RefreshFromMachine()` 경로)
   7. 완료 안내: "INPUT 카세트 Material Data를 초기화했습니다. 문을 닫고 START를
      누르면 매핑부터 다시 진행됩니다."

(기존 `INPUT-CST-DATA-ALL-CLEAR` 로그 컨벤션 미러). 차단 시에도 사유가 로그에 남아야 한다.

## 5. 검증 절차

1. **빌드**: `/p:OutDir=<임시경로>` 우회 빌드로 컴파일 확인(기본 빌드 금지).
2. **시뮬 가드 확인**: Auto/Manual/Ready 실행 중 버튼 → 차단 팝업.
   InputFeeder/InputStage에 웨이퍼 데이터가 있는 상태 → 차단 팝업 + 사유.
3. **시뮬 정상 경로**: 정지 상태에서 CST CLEAR → Input1/Input2 슬롯 전부 EMPTY,
   Cassette Mapped=N 확인 → START 시 매핑부터 재진행되는지 확인.
   재매핑이 자동으로 걸리지 않으면 **코드 추가하지 말고 즉시 보고**.
4. 저장 파일(Material 스냅샷) 갱신 확인 — 앱 재시작 후에도 EMPTY 유지.
