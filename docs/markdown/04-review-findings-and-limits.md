## 판단 범위

현재 변경은 추가 3점 실측 절차를 제거하면서, 기존 CONFIRM의 자료 일관성과 검출/보정/저장 보호를 유지하고 진단 로그를 보강하는 작업이다. 과거 간헐 쉬프트의 단일 원인이나 현재 장비 정상화를 입증한 작업이 아니다.

기존 완료/순서/저장/일관성 검사는 남으므로 모든 저장 자료가 무조건 재개된다는 뜻은 아니다. 반면 남은 실제 다이 수가 3개 미만이라는 새 절차의 제한은 제거된다. 최신 오프라인 183개와 격리 Build(오류 0개·기존 경고 41개)는 통과했고 결과는 03에서 관리한다.

## 2. 유지한 보호와 이번에 바꾼 내용

단발/누적 X/Y 기본 20 mm와 저장된 큰 값을 보존한다. 반 피치 상한·운영 설정 자동 변경은 추가하지 않는다. 기존 자동 Align의 피치/각도 판정은 그대로이며, 일반 CONFIRM이 별도 다점 품질 검사를 수행하지 않는다는 점을 분명히 한다.

## 3. 앞 단계의 3점 검증 검토 이력 — 현재 시작 절차 아님

앞 단계에서는 거의 일직선인 grid(0,0), (31,30), (32,31)의 수치 불안정을 피하기 위해 삼각형 높이/최장변 비율 0.1을 적용했다. 0.001 mm 가상 교란·회전·축척·반전 시험은 수학 정책의 테스트였으며 실제 장비 노이즈 측정이 아니었다.

이후 사용자에게 3점 선택과 점별 실제 다이 대응 확인을 요구하는 조작이 맞지 않음을 확인하여, 현재는 해당 UI와 이동/실측 절차를 필수 시작 경로에서 제거했다. 정책 함수나 과거 증거 자료형이 호환성 때문에 남아 있어도 현재 작업자에게 세 점 선택을 요구하지 않는다. 과거 3점 테스트를 새 CONFIRM의 물리 측정 합격으로 보고하지 않는다.

## 4. 부분 진행 Wafer와 구형 baseline

부분 진행 자료에서 원점·정규화 Die 상태/Bin/좌표·남은 순서가 현재 Material과 같으면 확인 메타데이터만 추가한다. 기존 전체 승인 UID 목록/revision/시작 기록과 실제 픽업된 다이 이력을 보존한다. 새로 실측할 다이가 세 개 필요하지 않다.

기존 전체 승인 순서와 revision이 없거나 이미 진행된 자재의 좌표·상태·순서를 바꾸려는 경우는 별개다. 앞선 STOP/Retry 등에서 순서가 소실됐다면 이번 확인 절차가 과거 순서를 임의 복구하지 않는다. 불일치를 실제 자재 전체 초기화 또는 자동 보호 우회로 해소하지 않는다.

baseline 없는 구형 자료는 현재 canonical Material과 동일한 좌표를 최초 기준으로 채택한다. 검출 전 기준 저장을 확인하며, CONFIRM 경로에서도 기준/승인 자료 저장을 확인한다. 이 결정은 이전 누적 Offset이 0이었다는 판정이 아니다. BASELINE 이벤트의 pastCumulativeRecovered=False와 새 기준 이후 누적량을 구분해야 한다. 기존 저장 baseline의 revision이 다르면 자동 재채택하지 않는다.

## 5. UI/STOP 보호와 물리 측정·로그의 한계

기존 결정 잠금과 수동 callback 종료 확인·JogStop·정지 확인·scope 해제 보호를 유지한다. 새 3점 이동·촬영·표시 영상별 확인 경로는 제거한다. 실제 STOP/지연 Vision/디스크 장애의 통합 시험은 미실시다.

1. **context 확인은 물리 실측이 아니다.** 저장된 맵이 일관돼도 실제 wafer가 미끄러졌거나 같은 패턴의 이웃 다이에 대응될 수 있다. 새 확인 자료는 context-confirmation-without-physical-measurement로 구분한다.
2. **DIE DETECTION은 선택한 기준에 대한 단일 raw 결과다.** captureX/Y/T는 촬영 직전, afterCenterMoveX/Y/T는 중심 이동 후다. 일반 스냅샷 actualCameraX/Y/T는 이벤트 작성 시점이므로 촬영값으로 바꿔 해석하지 않는다.
3. **기존 per-die AlignmentSnapshot의 시점도 구분해야 한다.** BuildInputStageAlignmentSnapshot은 결과 반영 시 actual 축을 읽는다. 선행 촬영에서는 이미 다음 위치일 수 있어 반드시 촬영 순간 좌표라고 해석하면 안 된다.
4. **PICKUP-TARGET는 계산된 목표의 증거다.** 기존 raw Vision/카메라/학습/기계 보정과 최종 목표를 저장하지만 실제 기계 도착이나 다이의 물리 픽업 성공까지 입증하지 않는다. 실제 Motion·Bottom 결과와 함께 비교한다.
5. **head slot은 콜렛 일련번호가 아니다.** pickupSide와 pickupHeadSlot은 해당 Front/Rear의 1~4번 위치다. 교체 전후 물리 콜렛의 고유 serial을 새로 추적한 것은 아니다.

3점 절차를 제거한 대신 현재 자료 보호와 로그는 남는다. 이 차이를 숨기고 모든 물리 문제를 방지한다고 주장하지 않는다.

## 6. Simulation과 비생산 수동 Review

기존 SKIP RUN REVIEW IN SIMULATION 설정에 따른 자동 skip 분기는 변경하지 않는다. Skip이 꺼진 수동 Review에서는 기존 CONFIRM을 사용한다. 현재 모드에 맞는 CONFIRM-CONTEXT-NONPRODUCTION/PRODUCTION 승인 자료를 구분하며 새 Measurements를 만들어 합격시키지 않는다.

기존 NONPRODUCTION-MANUAL 또는 SIMULATION-DEFAULT 자료는 과거 marker로 해석한다. 현재 모드·recipe·stage·wafer/map·세션/요청·저장 결과 조건은 계속 확인한다. 시뮬에서 그냥 시작되는 현상과 실제 장비의 인풋/픽업 정확도는 별개다.

## 7. 검증·로그 보존·성능의 해석

최신 수정본은 정책 30개·실제 Common 로그 정책 26개·최신 Handler Config 12개·Material geometry 10개·진행 보존 30개·기존 검증점 상태 16개·기존 비생산 marker/context 15개·새 확인/provenance/JSON 44개, 합계 183개 오프라인 검사를 통과했다. 4차 실제 등록 프로젝트 격리 Build도 오류 0개·기존 경고 41개로 통과했다. 중간 외부 작업 빌드 오류는 해당 작업이 직접 정리했고 이번 작업은 그 파일을 변경하지 않았다. 앞 단계의 113개는 당시 3점 구현을 포함한 이전 결과로 구분한다. 실제 UI/장비·저장 장애 통합 시험은 미실시다.

이번 개별 helper 40회 평균(1,257개 hash 3.487 ms/shape 0.360 ms, 1,645개 hash 4.306 ms/shape 0.415 ms)은 전체 승인·진단·잠금·디스크·장비 사이클 성능 측정이 아니다.

Review의 IN-REVIEW-*와 픽업 계산의 PICKUP-TARGET는 LogSeverity.Audit로 최소모드에서도 영속 대상으로 큐에 등록한다. 기존 자세한 픽업 로그를 보존하므로 상세모드에서는 같은 계산 메시지가 일반 로그와 Audit에 함께 남는다. 승인 소비 거부는 이유/상태 변경 중심으로 기록하며 50 ms 폴링 전체를 영속 로그로 바꾸지 않는다.

EventLogger는 비동기 writer다. Audit 지정은 저장 정책상 누락 방지이며, 디스크 실패/갑작스런 전원 차단까지 내구성이 확정됐다는 뜻은 아니다. 로그 쓰기 실패가 기존 계산·승인 결과를 바꾸지 않도록 처리한다. 새 PICKUP-TARGET는 계산마다 문자열과 큐 부하를 추가하므로 실장비 tact/장기간 로그 용량은 현장 확인 대상이다.

현장에서는 RAD↔JMB, 동일 Material, 재시작 유무를 분리하여 새 로그의 원점/T/pitch/한계·승인 자료와 UID별 Input raw/PICKUP-TARGET/Bottom 결과를 비교한다. 정확한 검색 코드와 순서는 [05](05-operation-and-log-guide.md)에 정리했다. 실제 장비 구동·배포·운영 설정 변경은 수행하지 않았으며 쉬프트 해결을 확정하지 않는다.
