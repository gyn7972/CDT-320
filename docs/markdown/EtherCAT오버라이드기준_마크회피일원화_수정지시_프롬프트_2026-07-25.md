# 작업 1 — EtherCAT `AxmOverridePos` 기준 보정: 현재 Command → **모션 구동 시작 위치**

## 배경 — 실장비 로그로 확정된 사실 (2026-07-25)

이 장비(아진 EtherCAT)의 `AxmOverridePos`는 오버라이드 값을 **"그 모션이 구동을 시작한 위치"
기준의 상대값**으로 해석한다. 벤더 주석(`AjinE\AXM.cs:766` "구동 시점의 위치를 기준으로한
Relative")의 "구동 시점"이 "오버라이드 호출 시점"이 아니라 "모션 시작 시점"이라는 뜻이다.

현재 코드(`AXM.ModifyPosition`, `:2129~`)는 `relative = 목표 − 현재 CommandPosition`으로 계산한다
— 기준이 틀렸다. 실장비 증거 (`D:\CDT-320\Log\Motion_2026-07-25.log` + Main 로그):

| 세션 (InputVisionX 선행이동) | 모션 시작 위치 | 보낸 relative | 실제 정지 위치 | 시작+relative |
|---|---|---|---|---|
| Rear 16:33:16 | 101.484 | 231.913 | **333.397** | **333.397** (오차 0.000) |
| Front 16:33:55 | 152.462 | 199.440 | **351.903** | **351.902** (오차 0.001) |
| Front 16:32:39 | ~152.36 | 206.589 | **358.953** | 일치 |

세 세션 모두 축이 정확히 `모션 시작 위치 + relative`에 멈췄고, 의도 목표(430.696/422.552/430.652)에
못 미쳐 `result=-5`("이동 완료 후 Command 위치가 목표와 다릅니다")로 실패했다
(`InputVisionXPrePosition ... 중간 안전대기점 이동이 실패했습니다. result=-5`).

같은 원리로 13:53 RearPickerX 폭주도 설명된다: 당시(변환 없던 빌드) 절대값 140.696을 그대로
보드에 넣었고, 보드는 `구동시작 700 + 140.696 = 840.7`(플레이스 방향)으로 해석해 역방향 폭주 →
서보 알람 0x0001.

## 수정 1-A. `AjinE\AXM.cs` — 모션 시작 위치 추적 + relative 기준 교체

### A-1. 축별 모션 시작 Command 기록
`#region 오버라이드 함수` 위쪽(또는 클래스 필드 영역)에:
```csharp
        // EtherCAT AxmOverridePos의 relative 기준 = "그 모션이 구동을 시작한 위치"
        // (실장비 검증 2026-07-25: 축이 정확히 시작위치+relative에 정지).
        // MovePosition이 이동 명령을 내리기 직전의 보드 Command 위치를 축별로 기록해 두고,
        // ModifyPosition이 그 값을 기준으로 relative를 계산한다.
        private static readonly System.Collections.Concurrent.ConcurrentDictionary<int, double> MotionStartCommandByAxis =
            new System.Collections.Concurrent.ConcurrentDictionary<int, double>();
```

### A-2. `MovePosition(int, double, double, double, double)`(`:2040`)에 기록 추가
`AxmMoveStartPos` 호출 **직전**에 현재 보드 Command를 읽어 저장한다:
```csharp
        public static int MovePosition(int axis, double position, double velocity, double acceleration, double deceleration)
        {
            int ret = 0;

            double startCommand = 0.0;
            if (GetCommandPosition(axis, ref startCommand) == 0)
                MotionStartCommandByAxis[axis] = startCommand;
            else
                MotionStartCommandByAxis.TryRemove(axis, out _);

            if ((ret = AXL.CheckErrorCode("AXM.AxmMoveStartPos", AXM.AxmMoveStartPos(axis, position, velocity, acceleration, deceleration))) != 0) return ret;
            return ret;
        }
```
(`out _` 문법이 이 언어 버전에서 안 되면 `double removed; TryRemove(axis, out removed);`로.)
- `:2048`의 TimeSpan 오버로드에도 동일하게 추가한다(호출부가 있으면 — 없으면 있는 그대로 두고
  보고만 한다).
- 정지 상태에서는 Command == Actual이므로 이 값이 곧 구동 시작 위치다.

### A-3. `ModifyPosition`(`:2129~`)의 기준 교체
현재 `GetCommandPosition`으로 `commandBase`를 읽어 `relative = position − commandBase`로 계산하는
부분을:
```csharp
            double startBase;
            bool hasStartBase = MotionStartCommandByAxis.TryGetValue(axis, out startBase);
            if (!hasStartBase)
            {
                // 시작 기록이 없으면(이 모션이 MovePosition 경유가 아님) 안전을 위해 오버라이드를
                // 거부한다 — 잘못된 기준으로 보드에 상대값을 보내는 것이 폭주의 원인이었다.
                LogOverrideCall("POSITION", axis, position, velocity, acceleration, deceleration, -2, "NoMotionStartBase");
                return -2;
            }

            double relative = position - startBase;
```
로 바꾼다. 이후 `AxmOverridePos(axis, relative)` / `AxmOverrideAccelVelDecel(...)` 호출과 실패 처리
구조는 유지하고, `LogOverrideCall`에 넘기던 `commandBase` 인자 자리에 `startBase`를 넘긴다.
로그 메시지의 라벨도 `cmdBase=` → `startBase=`로 바꾼다 (혼동 방지 — 이번 사고 분석에서 이 라벨로
기준을 오판할 뻔했다).
- **연속 오버라이드(팔로잉이 한 모션에 여러 번)**: 기준은 항상 같은 모션의 시작 위치이므로
  `MotionStartCommandByAxis`는 오버라이드 시 갱신하지 않는다. 다음 `MovePosition`에서만 갱신된다.
- `ModifyVelocity`(속도 오버라이드)는 위치 기준과 무관 — 손대지 않는다.

## 수정 1-B. `AjinAxis.cs` — 오버라이드 리다이렉트를 아는 -5 판정

기준이 고쳐지면 새 문제가 드러난다: 위치 오버라이드로 목표가 연장된 모션은, 원래 명령을 await하던
`MoveAbsoluteAsync`의 마지막 확인(`:1155` 부근 `if (Math.Abs(CommandPosition - targetPos) > tolerance)
→ FailMotion(-5, ...)`)에서 **정상적으로 리다이렉트된 경우에도 -5**가 난다 — CommandPosition은
오버라이드 목표로 갱신되는데 `targetPos`는 원래 값이기 때문이다. 선행이동 코디네이터의
`result=-5` 실패는 base 버그와 이 문제가 겹친 결과다.

### B-1. 리다이렉트 시리얼 필드 신설 (`AjinAxis` 인스턴스 필드)
```csharp
        // 이 축의 위치 오버라이드(리다이렉트) 성공 횟수. MoveAbsoluteAsync가 자신의 이동 중
        // 오버라이드가 있었는지 판정해 마지막 Command↔Target 확인(-5)을 건너뛰는 데 쓴다.
        private int _positionOverrideSerial;
```

### B-2. `TryOverridePosition`(`:303`) 성공 경로에 시리얼 증가
실장비 경로(`base.OverridePosition(targetPosition);` 직후, `:388` 부근)와 시뮬 경로(`:326` 부근)
**양쪽 모두**에 `System.Threading.Interlocked.Increment(ref _positionOverrideSerial);` 추가.

### B-3. `MoveAbsoluteAsync` 마지막 확인 수정
이동 시작부(명령 발행 전, `_motionStopSerial` 캡처하는 곳 부근)에서
`int overrideSerial = System.Threading.Volatile.Read(ref _positionOverrideSerial);` 캡처.
마지막 확인을:
```csharp
                bool redirectedByOverride =
                    System.Threading.Volatile.Read(ref _positionOverrideSerial) != overrideSerial;
                if (!redirectedByOverride && Math.Abs(CommandPosition - targetPos) > tolerance)
                    return FailMotion(-5, "ABS MOVE", /* 기존 메시지 유지 */ ...);
                if (redirectedByOverride)
                    QMC.Common.Log.Write("Motion", "SYSTEM", "AX-MOVE-REDIRECT",
                        Name + " 이동 중 위치 오버라이드로 목표가 변경되어 원래 목표 확인을 생략합니다. " +
                        "originalTarget=" + targetPos.ToString("F6") +
                        ", command=" + CommandPosition.ToString("F6") + " - Check");
```
로 바꾼다. **리다이렉트된 이동은 0(정상)으로 반환**한다 — 최종 목표 도달 확인은 오버라이드를 발행한
쪽(코디네이터의 `WaitInputStageAxisInPosition`, 팔로잉의 `WaitMoveCompleteAsync`)이 이미 수행한다.
- 명령 전용 이동 메서드(`:1179~1250` 부근, WaitUntilMoveDone 없이 명령만 발행하는 오버로드)에
  같은 -5 확인이 있으면 동일하게 처리하고, 없으면 손대지 않는다(확인 후 보고).

## [확인 요청 1] — 연속 오버라이드의 보드 리베이스 여부 (검증 필수)
실장비 증거는 "모션당 오버라이드 1회" 케이스뿐이다. 한 모션에 오버라이드를 2회 이상 발행하는
팔로잉에서, 2회째 이후의 기준이 여전히 "모션 시작 위치"인지 보드가 리베이스하는지는 미확정이다.
시뮬이 아닌 **실장비 검증 항목**으로 보고서에 명시하라:
- 팔로잉 1사이클에서 `AXM-OVERRIDE`(startBase/relative)와 축 최종 도달 위치를 대조해
  `최종 위치 == 마지막 오버라이드의 startBase + relative`인지 확인.
- 불일치하면 즉시 사용자에게 보고하고 팔로잉 경로 사용 중지를 권고한다(코드 추가 수정 금지).

# 작업 2 — 마크검사(선행검사) 배치 종료 회피를 픽업 이연·팔로잉으로 일원화

## 배경 — 실장비 로그로 확정된 사실

픽업의 "이연 → 피커X 팔로잉" 오버랩(#17 + 이연 수정)은 정상 동작한다(16:10:52 로그로 확인,
acc=350 스케일 정상). 그런데 그 후 배치들에서 팔로잉이 전혀 나타나지 않는 이유:

```
16:10:52.725  InputCameraMarkInspectionSequence > InputVisionX avoid confirmed after
              input camera mark inspection. mode=minimal, target=160.644150   ← 여기서 이미 회피 완료
16:33:01.252  PickerPickUpSequence > ... 회피 좌표를 확정했습니다 ... hold=current(전진 금지 - B안)
              ← 픽업 시점엔 비전이 이미 회피 위치 → 이동 없음 → 팔로잉 대상 없음
```

**`InputCameraMarkInspectionSequence.MoveInputVisionXToAvoidAsync`(`:468~616`)가 배치 촬영 종료
직후, 픽업 허가(GrantPickUpPermission) 전에 비전을 동기로 최소 회피시킨다.** 이 이동은 피커가
아직 진입 허가도 받기 전이라 아무도 따라갈 수 없다. 사용자가 요구하는 "비전 회피 중 피커X 추종
동시 기동"이 성립하려면 이 회피를 없애고, 회피를 픽업 시퀀스의 이연·팔로잉 한 곳으로 모아야 한다.

## 수정 2-A. `MoveInputVisionXToAvoidAsync`에 위임 분기 추가

`IsMinimalRetreatGateSatisfied()`(`:507`에서 이미 사용 중인 게이트 — Auto + PickUp Conti 계열)가
**충족되면 회피 이동을 생략하고 픽업에 위임**한다. `:504`의 `double target = avoid;` 앞(또는
게이트 판정 직후)에:

```csharp
                // 기존 조건: 배치 촬영 종료 직후 이 시퀀스가 비전을 동기로 최소 회피시켰다 —
                //           픽업 허가 전이라 피커가 추종할 수 없어, 픽업의 이연·팔로잉(#17)이
                //           항상 hold=current(이동 없음)로 무력화됐다(실장비 로그 2026-07-25).
                // 현재 기준(사용자 지시 2026-07-25): Auto+Conti(이연·팔로잉이 동작하는 조건)에서는
                //           회피를 픽업 시퀀스로 위임한다 — 비전은 마지막 촬영 위치에 머물고,
                //           픽업의 MoveInputVisionToAvoidForPickerMove가 이연 후 피커X 팔로잉과
                //           동시 기동한다. 피커 X 일반 이동 폴백은 "이연 회피 완료 후 진입" 안전
                //           불변식이 지키고, 존/페어 인터락은 그대로 살아 있다.
                if (IsMinimalRetreatGateSatisfied())
                {
                    WriteLog("InputCameraMarkInspectionSequence",
                        Name + " InputVisionX 선행검사 후 회피를 픽업 이연·팔로잉으로 위임합니다(이동 생략). " +
                        "actual=" + (stage.CameraX != null ? stage.CameraX.ActualPosition.ToString("F6") : "-") +
                        ", side=" + Side + " - Check");
                    CurrentStep = InputCameraMarkInspectionStep.GrantPickUpPermission;
                    return 0;
                }
```

배치 규칙:
- 이 분기는 `IsInputCameraPreInspectionMode()`의 `AcquireInputStageAreaAsync`(`:486~490`) **뒤**,
  최소 회피 좌표 계산(`:507~545`) **앞**에 둔다 — 좌표 계산 자체가 불필요해진다.
- 게이트 미충족(비Conti/수동)이면 기존 코드 완전 무변경 — 전체 Avoid 동기 이동 그대로.
- `:588~609`의 최종 위치 확인(F3 강확인/avoid 확인)은 위임 분기에서 실행되지 않는다(early return).
- InputStageArea 등 리소스 획득/반환 흐름은 바꾸지 않는다 — 위임 분기의 return 0 이후 기존
