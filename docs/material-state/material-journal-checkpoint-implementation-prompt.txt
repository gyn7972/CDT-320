2. 작업 목표
-----------

현재 Material 전체 Snapshot 지연 저장을 다음 구조로 변경한다.

Auto Material 변경
  → MaterialStateService._stateSync 안에서 Runtime 상태 변경
  → Journal Epoch/Sequence 발급
  → 실제 변경 필드만 가진 독립 Delta 생성
  → 메모리 Queue 등록
  → _stateSync 해제
  → Auto 시퀀스 즉시 계속

별도 Journal Writer
  → Delta를 Sequence 순서대로 파일 Append
  → 50~100ms 또는 설정된 건수 단위로 Batch Flush
  → 실제 디스크 Flush 성공 후에만 LastDurableSequence 갱신

별도 Checkpoint Worker
  → Journal 전용 Projection에 같은 Delta를 순서대로 적용
  → Auto Runtime State 전체를 복사하지 않음
  → Idle/LOT 완료/프로그램 종료 시 Projection 전체를 material_state.json으로 저장
  → Checkpoint 성공 후에만 반영 완료 Journal을 회전 또는 정리

추가 목표:

- Auto Hot Path에서 전체 MaterialSnapshot 딥클론과 전체 JSON 쓰기를 제거한다.
- material_state.json에 Empty/Unknown/미참조 Wafer·Die가 계속 쌓이지 않게 한다.
- Journal 자체도 무한 증가하지 않도록 Checkpoint Sequence 기준 회전·정리한다.
- 프로그램 비정상 종료 후 Checkpoint + Journal Replay로 마지막 Durable Sequence까지 복구한다.
- Manual 편집/Data Clear처럼 작업자가 저장 성공을 확인해야 하는 기능은 지정 Sequence까지 Flush 결과를 UI에 반환한다.
- 기존 Material 위치·상태 전이, LOT 정책, CSV 측정 데이터, UI StateChanged 의미를 바꾸지 않는다.

3. 현재 코드에서 확정된 구조
--------------------------

3.1 현재 저장 방식

Material 변경
  → MaterialStateService.NotifyAndSave()
  → RequestStateChanged()
  → RequestBackgroundSave()
  → 1초 Quiet 대기
  → 마지막 저장 이후 최소 5초 간격 대기
  → _stateSync 안에서 MaterialSnapshot 전체 딥클론
  → _stateSync 밖에서 material_state.json 전체 직렬화 및 원자 교체

근거 파일:

- QMC.CDT-320\Equipment\Materials\MaterialStateService.cs
  - _stateSync 및 저장 제어 필드: 18~38 부근
  - NotifyAndSave/TryNotifyAndSave: 9131 부근
  - Background Worker: 9187 부근
  - SaveCurrentSnapshot: 9308 부근
- QMC.CDT-320\Equipment\Materials\MaterialSnapshotStore.cs
  - 경로 정의: 18~25 부근
  - CreateSaveCopy: 624 부근
  - 전체 Snapshot Save: 681 부근
  - 딥클론: 887 부근
  - Temp → Backup → 원자 교체: 991 부근

현재 material_state.json은 Append 파일이 아니다. 매 저장 시 전체 파일이 교체된다.
그러나 MaterialSnapshot.Wafers와 MaterialSnapshot.Dies가 런타임에 남아 있기 때문에 저장 파일 내부 객체 수와 크기가 증가한다.

코드 주석에는 다음 실측이 기록되어 있다.

- material_state.json 3.9MB → 7.5MB 증가
- 전체 저장 1회 343~447ms
- 검사 상세가 포함되면 10MB 이상 및 0.3~1.2초 수준 가능

따라서 현재의 5초 병합 저장은 저장 횟수만 줄였고, _stateSync 안의 전체 딥클론이 Auto Material 변경을 기다리게 할 가능성은 남아 있다.

3.2 데이터 누적 원인

- MaterialSnapshot은 Cassettes/Wafers/Dies 전체 목록을 저장한다.
- Wafer 생성은 State.Wafers.Add, Die 생성은 State.Dies.Add를 사용한다.
- 카세트 Data Clear의 여러 경로는 Wafer를 Empty/Unknown으로 변경하지만 항상 State.Wafers에서 제거하지 않는다.
- 연결 Die도 모든 Clear 경로에서 제거되는 것은 아니다.
- LOT 완료는 Lot 이력과 통계를 저장한 후 Material LOT ID만 비우며, 전체 Material 컬렉션을 정리하지 않는다.
- 새 Mapping 시 일부 Finished/Stale Material 제거가 있지만 특정 Mapping 조건에만 적용된다.
- SaveMaterialInspectionDetail=false는 저장 사본의 Measurements/Alignments만 비울 뿐 Wafer/Die 객체 수를 줄이지 않는다.

따라서 LOT 완료, 카세트 Clear, 자재 교체를 반복하면 물리 위치와 참조가 끊긴 Empty/Unknown Material이 전체 Snapshot에 남을 수 있다.

3.3 현재 저장·복구 위험

- 동기 Flush와 Background Save가 각각 다른 시점의 전체 사본을 만들 수 있으므로 Sequence가 없으면 오래된 사본이 나중에 저장되는지 검증이 어렵다.
- MaterialSnapshotStore의 Fallback 후보 선택에는 최신 시각과 데이터 양 점수가 사용된다.
- Journal 적용 후에는 데이터가 많다는 이유로 과거 Snapshot을 선택하면 삭제된 Material이 되살아날 수 있으므로 Epoch/CheckpointSequence 기준으로 바꿔야 한다.
- Clear는 단순 Upsert가 아니라 Tombstone/Remove Delta로 기록하지 않으면 Replay 시 삭제 데이터가 복원될 수 있다.
- D:\CDT-320\State에는 현재 소스가 사용하지 않는 과거 material_journal_*.log가 존재할 수 있다. 이를 신규 Journal로 자동 Replay하거나 삭제하지 않는다.
- 과거 Journal이 전체 Die/Inspection 상세를 담았다면 작은 Delta가 아니므로 구조를 그대로 복원하지 않는다.

3.4 별도 저장 영역

- machine_state.json 저장과 Material 저장은 별도다.
- 이번 작업에서 MachineRuntimeState 저장 병합 구조를 Material Journal에 섞지 않는다.
- 기존 검사/생산 CSV Writer는 이력 저장 역할을 유지한다.
- material_state.json은 장비 재개에 필요한 현재 상태 Checkpoint로 제한하고 장기 이력 저장소로 사용하지 않는다.

5. 권장 클래스 구조
-----------------

구조는 읽기 쉽게 다음 책임으로 나눈다. 실제 파일명은 최신 코드와 중복 여부를 확인한 후 확정한다.

5.1 MaterialDelta.cs

- Runtime 변경 한 건 또는 의미 있는 원자 작업의 작은 변경값을 표현한다.
- Runtime WaferMaterial/DieMaterial 객체 참조를 보관하지 않는다.
- 변경 순간 값만 복사한 immutable DTO를 사용한다.
- 최소 포함 정보:
  - SchemaVersion
  - EpochId
  - Sequence
  - OperationId
  - OccurredAtUtc
  - Reason
  - OperationKind
  - 대상 Entity 종류/ID
  - 변경 필드 또는 Remove Tombstone

권장 Delta 범주:

- SnapshotHeaderPatch
- CassettePatch
- CassetteSlotPatch
- WaferPatch / WaferRemove
- DiePatch / DieRemove
- InspectionSummaryUpsert / InspectionRemove
- BulkMappingChunk

Delta에서 매번 전체 DieMaterial이나 전체 MaterialSnapshot을 직렬화하지 않는다.
SaveMaterialInspectionDetail=false이면 Measurements/Alignments 상세를 Journal에도 넣지 않는다.
상세 측정 데이터는 기존 CSV 저장 경로를 유지한다.

5.2 MaterialJournalEntry.cs

- 파일에 기록할 단일 Frame/Record 계약이다.
- SchemaVersion/Epoch/Sequence/Length/Checksum 또는 동등한 손상 검출 정보를 포함한다.
- 마지막 Record가 쓰다 중단된 경우 마지막 불완전 Record만 무시할 수 있어야 한다.
- 중간 Sequence 누락, 역전, 중복, Checksum 불일치는 Recovery Required로 처리한다.

5.3 MaterialJournalStore.cs

- Journal 파일 Append와 Batch Flush만 담당한다.
- 하나의 장기 실행 Writer만 파일을 소유한다.
- Material 변경마다 Task.Run을 생성하지 않는다.
- Queue 순서를 그대로 유지한다.
- 50~100ms 또는 설정 건수 도달 시 Batch Write/Flush한다.
- LastDurableSequence는 FileStream Flush 성공 후에만 증가한다.
- Disk Full/권한/IO 오류를 숨기거나 Delta를 버리지 않는다.
- Queue 길이와 High Watermark를 계측한다.
- Writer 장애가 지속되면 Persistence Unhealthy를 알리고 Auto를 안전 경계에서 정지시키는 정책을 계획에 포함한다.

5.4 MaterialJournalProjection.cs

- Checkpoint 생성 전용 MaterialSnapshot을 보유한다.
- 시작 시 Checkpoint를 로드한 뒤 Journal을 Sequence 순서로 Replay한다.
- 이후 Writer가 Durable 처리한 Delta를 동일 순서로 적용한다.
- Auto Runtime State를 전체 복제하지 않는다.
- 같은 Delta를 두 번 적용해도 중복 데이터가 생기지 않도록 Sequence/OperationId를 검증한다.

5.5 MaterialCheckpointWorker.cs

- Projection만 읽어 material_state.json Checkpoint를 생성한다.
- Runtime MaterialStorage.State를 순회하거나 Clone하지 않는다.
- Idle/LOT 완료/프로그램 종료와 승인된 수동 Flush 경계에서 실행한다.
- 기존 Temp → Backup → 원자 교체의 안전성을 유지한다.
- Checkpoint에 EpochId와 CheckpointSequence를 저장한다.
- Checkpoint 성공 전에는 해당 Sequence 이하 Journal을 삭제하거나 회전하지 않는다.
- 성공 후 Journal을 세대별로 회전하고 보존 개수/기간을 제한한다.

5.6 MaterialPersistenceCoordinator.cs

- Sequence 발급, Queue 등록, Writer/Projection/Checkpoint 생명주기를 한곳에서 관리한다.
- 다음 상태를 명시한다.
  - LastIssuedSequence
  - LastQueuedSequence
  - LastWrittenSequence
  - LastDurableSequence
  - LastCheckpointSequence
  - IsHealthy
- Manual/UI용 FlushThrough(sequence, timeout) API를 제공한다.
- Auto 변경은 Queue 등록 후 바로 반환한다.
- 종료 시 신규 변경 접수를 닫고 Queue Drain → Durable Flush → Checkpoint 순서로 종료한다.

5.7 MaterialStateCompactor.cs

- material_state.json과 Runtime State의 미참조 Material 누적을 함께 해결한다.
- Checkpoint 사본에서만 몰래 제외하지 않는다.
- 안전 경계에서 Runtime과 Projection에 동일한 Remove Delta를 적용한다.
- 어떤 항목을 왜 제거했는지 Count와 ID Sample을 로그에 남긴다.

6. Material 변경 원자 경계
-----------------------

모든 Journal 대상 변경은 다음 순서를 지킨다.

1) 필요한 Delta 값을 미리 준비한다.
2) _stateSync 획득
3) Runtime 상태 변경
4) 같은 Lock 안에서 Sequence 발급
5) Runtime 객체 참조가 없는 Delta 완성
6) Queue 등록
7) _stateSync 해제
8) StateChanged 요청
9) Auto는 즉시 다음 Step으로 진행

금지:

- _stateSync 안에서 파일 Open/Write/Flush/Checkpoint 생성
- _stateSync 안에서 전체 MaterialSnapshot 복제
- Runtime 객체를 Delta에 그대로 저장
- 상태만 바꾸고 Delta를 나중에 추정하여 생성
- 같은 변경을 NotifyAndSave와 Journal 양쪽에서 중복 저장
- Queue 실패를 성공으로 반환

현재 일부 메서드는 _stateSync 밖에서 State 목록이나 객체를 직접 변경한다. Journal 적용 전 변경 경로별 Lock 범위를 확인하고, 한 번에 대규모 재작성하지 말고 기능군별로 정리한다.

7. Bulk Mapping 처리
------------------

Mapping은 수백~수천 Die를 생성하므로 일반 Die Patch 한 건과 다르게 취급한다.

- 하나의 거대한 JSON Line이나 전체 MaterialSnapshot Delta를 만들지 않는다.
- 설정된 최대 항목 수 또는 최대 Byte 기준으로 BulkMappingChunk를 나눈다.
- 모든 Chunk에 OperationId, ChunkIndex, ChunkCount를 기록한다.
- Replay 중 Chunk 누락 시 Mapping 전체를 완료로 인정하지 않는다.
- Mapping 완료 후 Idle 경계에서 Checkpoint를 요청할 수 있다.
- Mapping 중간 Crash 시 완료된 Chunk까지만 임의 사용하지 말고 Mapping Recovery Required 또는 안전한 재매핑 정책을 명시한다.

8. material_state.json 컴팩션 규칙
--------------------------------

단순히 오래됐다는 이유로 삭제하지 않는다. 물리 위치와 참조 관계를 기준으로 Reachability를 계산한다.

반드시 유지:

- 모든 Cassette Slot이 WaferId/WaferInstanceId로 참조하는 Wafer
- Input/Output Feeder, Input/Output Stage에 실제 존재하는 Wafer
- Front/Rear Picker에 있는 Die
- 예약 중인 Die
- 현재 진행 LOT 복구에 필요한 Material
- Output Cassette 교체 전 Finish Bin Material
- Wafer.DieIds가 참조하는 Die
- OutputReceiveSlots의 SourceDieUid/DieUid가 참조하는 Die
- 센서와 Material 불일치 복구 판정에 필요한 현재 Material

제거 후보:

- State=Empty
- CurrentLocation=Unknown
- Cassette Slot 참조 없음
- Feeder/Stage/Picker 참조 없음
- Pick/Place 예약 없음
- 활성 Wafer.DieIds/OutputReceiveSlots 참조 없음
- 현재 LOT 또는 Recovery Required 판정에 필요하지 않음

중요:

- LOT 완료만으로 실제 Output Cassette에 남아 있는 제품을 삭제하지 않는다.
- Data Clear는 삭제 대상 Wafer/Die의 Tombstone Delta를 발행한다.
- 삭제된 Wafer/Die의 역참조도 함께 정리한다.
- LOT/검사 장기 이력은 LotStorage와 CSV에 남기고 현재 Material Checkpoint에는 중복 보존하지 않는다.
- 컴팩션 전후 Cassettes/Wafers/Dies/Inspection/Byte 수를 기록한다.

9. Startup Recovery 순서
----------------------

1) 유효한 material_state.json Checkpoint 후보를 읽는다.
2) EpochId/CheckpointSequence가 가장 높은 정상 Checkpoint를 선택한다.
3) Legacy Version 2 Snapshot은 Epoch 없음/Sequence 0으로 명시적으로 마이그레이션한다.
4) CheckpointSequence보다 큰 Journal Record만 순서대로 Replay한다.
5) Sequence 누락·역전·중복·Checksum 오류를 검사한다.
6) 잘린 마지막 Record만 안전하게 무시하고 로그에 남긴다.
7) 복구 Projection 검증 후 MaterialStorage.ReplaceState를 한 번 수행한다.
8) 실제 센서·축·카세트 상태와 비교한다.
9) 불일치하면 기존 정책대로 Recovery Required로 Auto를 차단한다.
10) Next Sequence는 마지막 Replay Sequence + 1로 시작한다.

금지:

- 데이터 수가 더 많다는 이유로 과거 Recovery/Backup Snapshot을 선택
- 알 수 없는 과거 material_journal_*.log 자동 Replay
- Journal 오류를 무시하고 최신 상태라고 표시
- 저장값만 믿고 Auto 이동 재개

10. 생명주기 연결
----------------

Auto 변경:

- Queue 등록까지만 동기 처리
- Full Snapshot/Checkpoint 대기 금지

Manual 편집/Data Clear/Map Transfer:

- 변경에서 발급된 Sequence를 받는다.
- FlushThrough(sequence, timeout) 결과를 UI 성공 여부에 반영한다.
- 실패 시 신규값이 메모리에만 남았음을 사용자에게 명확히 알린다.

Idle:

- Writer가 현재 Sequence까지 Durable한지 확인한다.
- 필요할 때 Projection Checkpoint와 컴팩션을 실행한다.
- Auto가 다시 시작되면 무거운 Checkpoint 시작을 보류하거나 취소 가능한 안전 정책을 둔다.

LOT 완료:

- Lot 이력/통계 저장
- Material LOT ID 변경 Delta
- 물리적으로 사용 중인 Material 보존 조건 확인
- 미참조 Material 컴팩션 Delta
- Journal Durable Flush
- Checkpoint
- Checkpoint 성공 후 Journal 회전

프로그램 종료:

- 신규 변경 접수 종료
- Queue Drain
- 마지막 Sequence Durable Flush
- Projection Checkpoint
- Writer Dispose
- 실패 시 기존 종료 확인 UI와 같은 수준으로 손실 가능성을 알린다.

Emergency/Cycle Stop:

- 장비 정지를 파일 저장보다 우선한다.
- 안전 정지 후 Journal Flush를 요청한다.
- 긴 전체 Checkpoint가 안전 정지를 지연시키지 않게 한다.

11. 단계별 작업 순서
-----------------

반드시 다음 순서로 진행한다.

1단계: 최신 코드 재분석

- 모든 Material 변경 경로와 현재 Lock/저장 시점을 표로 작성
- Auto Hot Path와 Manual Durable 경로 구분
- current material_state.json의 크기와 Cassettes/Wafers/Dies/Inspection 수 계측
- Save elapsed 및 _stateSync 보유 시간 기준값 확보
- 코드 수정 금지

2단계: 계획·체크리스트 보고 및 사용자 승인

- 신규/수정 파일 목록
- Delta 종류별 호출처 매핑
- Startup/Shutdown/LOT/Idle 연결 순서
- 마이그레이션과 Rollout 방법
- 실패 정책과 잔여 위험
- 검증 체크리스트
- 사용자 승인을 기다린다.

3단계: Journal 데이터 계약과 Writer 골격

- Delta/Entry/Store/Coordinator 생성
- 아직 기존 저장 경로를 제거하지 않는다.
- Sequence/CRC/Batch/Flush 단위 테스트 또는 정적 Harness 작성
- C# 7.3 호환 확인

4단계: Projection과 Startup Replay

- Legacy Snapshot 마이그레이션
- Checkpoint + Journal Replay
- Sequence/손상 검증
- 실제 Runtime 반영은 검증된 Projection으로 한 번만 수행

5단계: Material 변경 경로 이관

- 기능군별로 순차 이관한다.
  1. Pick 예약/해제/Pick 완료
  2. Bottom/Side/Output 검사 요약
  3. Place/Output Receive
  4. Wafer 이동
  5. Cassette Mapping/Data Clear
  6. LOT ID/Recipe Context
  7. Manual UI 변경
- 각 기능군 이관 후 Delta Replay 결과를 기존 Runtime 최종 상태와 비교한다.
- 모든 경로가 이관되기 전에는 기존 NotifyAndSave를 무조건 삭제하지 않는다.

6단계: Checkpoint와 컴팩션

- Projection 기반 Checkpoint
- Reachability 기반 Runtime/Projection 공통 Remove Delta
- LOT 완료/Idle/종료 연결
- Journal 회전과 보존 정책

7단계: Legacy 전체 저장 Hot Path 제거

- Auto NotifyAndSave가 전체 Snapshot Worker를 시작하지 않게 한다.
- Manual Flush는 FlushThrough(sequence)를 사용한다.
- 필요하면 Feature Flag를 두되, Journal 활성 상태에서 Auto Full Snapshot Dual Write로 택타임을 다시 악화시키지 않는다.

8단계: 검증

12. 안전·호환 불변조건
--------------------

- MaterialStorage.State와 MaterialStateService가 Runtime 단일 기준이다.
- UI/Grid 자체 데이터를 기준 상태로 사용하지 않는다.
- 기존 Material ID, WaferInstanceId, DieId, Cassette Role, Location 의미를 바꾸지 않는다.
- 기존 JSON 직렬화 키를 제거하거나 이름 변경하지 않는다.
- Snapshot Version 변경 시 Legacy Version 2 마이그레이션을 제공한다.
- Pick/Place/Inspection/Mapping의 업무 결과를 바꾸지 않는다.
- StateChanged 이벤트는 Runtime 변경을 빠르게 표시하며 Durable 완료 이벤트와 분리한다.
- Disk 오류를 성공으로 바꾸지 않는다.
- Delta를 조용히 Drop하지 않는다.
- Checkpoint 성공 전에 Journal을 정리하지 않는다.
- 저장 상태와 실물 센서가 다르면 Auto를 차단한다.
- Journal/Checkpoint 때문에 Motion/Interlock/전체 초기화 코드를 변경하지 않는다.
- 과거 Journal/Recovery/Manual Backup 파일은 사용자 승인 없이 삭제하지 않는다.

13. 필수 계측과 로그
-----------------

다음 값을 운영 로그에 남긴다.

- EpochId
- LastIssuedSequence
- LastQueuedSequence
- LastWrittenSequence
- LastDurableSequence
- LastCheckpointSequence
- Queue Length/Max
- Batch Count/Bytes/WriteMs/FlushMs
- _stateSync mutation 보유 시간 평균/P95/Max
- Checkpoint Wafers/Dies/Bytes/ElapsedMs
- Compaction 제거 Wafer/Die 수와 보존 수
- Replay Record 수/시작 Sequence/마지막 Sequence/ElapsedMs
- Writer 오류와 재시도 횟수

Auto 매 Die마다 상세 로그를 남겨 택타임과 로그 용량을 악화시키지 않는다. Batch 요약과 Slow/Failure 기준 로그를 사용한다.

14. 첫 응답 요구사항
-----------------

첫 응답에서는 코드를 수정하지 말고 다음만 보고한다.

1) 현재 Material 변경 → 저장 → 복구 호출 구조
2) 모든 NotifyAndSave/TryFlushPendingSave 호출처 분류표
3) material_state.json 누적 원인의 코드 근거
4) 제안 클래스 관계와 파일 목록
5) Delta 종류와 각 호출처 매핑
6) Startup/Auto/Manual/Idle/LOT 완료/종료 흐름
7) 단계별 구현 계획
8) 안전·복구·성능 위험
9) 검증 체크리스트
10) 사용자 승인 요청

사용자가 명시적으로 승인하기 전에는 코드, csproj, 설정, 운영 데이터를 수정하지 않는다.
