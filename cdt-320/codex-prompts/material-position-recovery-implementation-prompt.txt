CDT-320 Material 위치 이동/복구 UI 구현 프롬프트

작성일: 2026-07-23

======================================================================
1. 작업 기준과 절대 규칙
======================================================================

대상 소스는 반드시 아래 로컬 저장소 하나만 사용한다.

D:\Source\CDT-320_New

다른 CDT-320 소스 폴더, 예전 체크아웃, 다운로드 폴더, 배포 폴더의
코드를 참고하거나 복사하지 않는다.

D:\CDT-320은 장비 실행 파일, 운영 데이터, 로그가 있는 배포 영역이다.
소스 기준으로 사용하거나 빌드 결과로 덮어쓰지 않는다.

작업 시작 전에 반드시 다음을 확인하고 보고한다.

- git rev-parse --show-toplevel
- 현재 브랜치
- git status --short --branch
- 기존 수정/추가 파일
- 기존 변경과 이번 작업 대상 파일의 중첩 여부

기존 변경 사항은 절대 되돌리거나 덮어쓰지 않는다.

다음 Git 작업은 실행하지 않는다.

- commit
- push
- pull
- merge
- rebase
- reset
- checkout을 이용한 롤백
- clean

Clean/Rebuild를 실행하지 않는다.
Build가 필요하면 반드시 별도 OutDir을 지정한 /t:Build만 실행한다.

WinForms 컨트롤 선언, 생성, 속성, 배치, 이벤트 연결은
반드시 *.Designer.cs의 InitializeComponent() 안에 인라인으로 작성한다.
기능, 검증, Material 처리 로직은 일반 *.cs 또는 Service에 작성한다.

이번 기능은 Material 상태와 Auto 재개 조건에 영향을 줄 수 있다.
시퀀스, 인터락, Auto 시작 차단 조건을 변경해야 한다면
현재 동작과 수정안을 먼저 보고하고 사용자의 명시적 승인을 받은 뒤 구현한다.

======================================================================
2. 기능 목표
======================================================================

Wafer/Bin의 현재 위치 정보를 아래 흐름으로 UI에서 확인하고,
필요한 경우 안전하게 이동 또는 복구할 수 있도록 한다.

INPUT WAFER

[Input Cassette 1/2 + Slot] <-> [Input Feeder] <-> [Input Stage]

OUTPUT BIN

[GOOD1 / GOOD2 / NG Cassette + Slot] <-> [Output Feeder]
                                      <-> [GOOD / NG Stage]

두 동작은 반드시 분리한다.

1) PHYSICAL TRANSFER

- 실제 장비가 움직이며 제품을 이송한다.
- 기존 InputFeederPage/OutputFeederPage의 수동 Feeder Sequence를 재사용한다.
- 센서 인계 확인 후 기존 Sequence가 Material 위치를 갱신한다.
- Material API를 UI에서 직접 호출하여 실제 모션과 데이터를 분리하지 않는다.

2) MATERIAL DATA RECOVERY

- 실제 장비를 움직이지 않는다.
- 실물은 이미 수동 복구되어 있고 Material 데이터 위치만 틀린 경우 사용한다.
- Maintenance 이상의 권한과 명시적인 확인 절차를 요구한다.
- UI에서 MaterialStateService.MoveWafer()를 직접 호출하지 않는다.
- 전용 Domain/Recovery Service를 통해서만 변경한다.

이 프롬프트의 신규 구현 핵심은 MATERIAL DATA RECOVERY다.
기존 물리 이송 시퀀스의 순서와 인터락은 변경하지 않는다.

3. 현재 소스에서 반드시 재확인할 사항
======================================================================

아래 분석 결과를 현재 소스에서 다시 검증한다.

1) WorkTab의 CST STATUS

- WorkTab.cs의 BtnInputCst/BtnOutputCst는 CstStatusDialog를 여는 액션 버튼이다.
- CstStatusDialog는 약 500ms 주기의 조회용 모니터다.
- 현재 슬롯은 동적으로 만든 Label이며 선택/이동 기능이 없다.
- SourceCassetteRole/SourceSlotNumber를 기준으로 Feeder/Stage에 이동한 제품도
  원래 Cassette slot에 표시할 수 있다.

따라서 기존 CST STATUS를 직접 편집/drag-drop 화면으로 바꾸지 않는다.

2) WorkInfo 구조

- WorkInfoTab에는 InputCassette/InputFeeder/InputStage와
  OutputStage/OutputFeeder/OutputCassette 페이지가 이미 등록되어 있다.
- InputFeederPage와 OutputFeederPage에는 다음 물리 이송 버튼이 있다.
  - CST -> FEEDER
  - FEEDER -> STAGE
  - STAGE -> FEEDER
  - FEEDER -> CST
- 위 버튼은 ManualActionScope와 기존 Feeder Sequence를 호출한다.

3) Material 단일 기준

- MaterialStorage.State
- MaterialStateService

Grid, Label, CassetteSlotView, Unit 화면은 View/Projection일 뿐
Material의 단일 기준으로 사용하지 않는다.

4) 기존 API

- MaterialStateService.MoveWafer()
  - 대상 위치의 다른 Material 중복은 확인한다.
  - Cassette slot 제거, CurrentLocation/State 갱신, Trace/Save를 수행한다.
  - 그러나 Auto 상태, 허용 경로, 물리 센서, GOOD/NG,
    Unit runtime cache까지 모두 처리하지 않는다.

- MaterialStateService.PutWaferInCassette()
  - Cassette enabled/present/mapped 상태
  - slot 범위 및 slot/ID 일관성
  - 대상 덮어쓰기
  - 원본 Cassette/slot 반환
  을 강하게 검사한다.

- CreateWaferAtLocation()/ClearWaferAtLocation()은 생성/삭제 기능이다.
  Material 이동 기능에 재사용하지 않는다.

5) Runtime Projection

- InputFeederUnit.CurrentWaferMaterial
- InputStageUnit.CurrentWaferMaterial
- OutputFeederUnit MaterialState
- Input active die map/cache
- Input Die reservation/Permission
- Output stage receive plan
- Sequence Signal 상태

MaterialStorage만 바꾸고 위 Projection을 방치하지 않는다.

4. 권장 UI 위치와 구조
======================================================================

주 기능은 작업 정보(WorkInfoTab) 사이드 메뉴 아래의 신규 전용 페이지로 만든다.

권장 이름:

- 사이드 메뉴: MATERIAL POSITION
- 페이지 클래스: MaterialPositionRecoveryPage
- 기능 제목: MATERIAL FLOW / DATA RECOVERY

기존 작업 -> MAIN -> INPUT/OUTPUT CST STATUS는 조회 전용으로 유지한다.
필요하면 CST STATUS에 "MATERIAL POSITION 열기" 버튼만 추가하되,
1차 구현에서는 생략 가능하다.

권장 권한:

- 조회: Operator 이상
- DATA RECOVERY 적용: Maintenance 이상
- Admin도 적용 가능

권한은 UI Enabled만으로 끝내지 말고 적용 Service 진입부에서 다시 검사한다.

======================================================================
5. UI 상세 계약
======================================================================

페이지에는 INPUT WAFER와 OUTPUT BIN을 명확히 분리한다.

INPUT WAFER:

- Input Cassette 1/2 slot 목록
- Input Feeder 단일 위치
- Input Stage 단일 위치
- 인접 방향별 이동/복구 버튼

OUTPUT BIN:

- GOOD1/GOOD2/NG Cassette slot 목록
- Output Feeder 단일 위치
- Output GOOD Stage
- Output NG Stage
- 인접 방향별 이동/복구 버튼

각 위치 카드에는 다음 항목을 표시한다.

- 위치 이름
- 실제 감지 상태: DETECTED / EMPTY / UNKNOWN
- Material ID
- Material State
- CurrentLocation
- Source Cassette Role
- Source Slot
- Output Grade
- UpdatedAt
- 정합 결과: MATCH / MISMATCH / RECOVERY REQUIRED

화면 상단에는 아래 경고를 항상 표시한다.

"MATERIAL DATA ONLY - 이 기능은 장비를 움직이지 않습니다.
 실제 제품 위치를 확인한 후 사용하십시오."

DATA RECOVERY는 drag/drop으로 구현하지 않는다.
다음의 명시적 절차를 사용한다.

1. 점유된 Source 선택
2. 비어 있는 인접 Destination 선택
3. 변경 전/후 Preview 표시
4. 실제 센서 상태 표시
5. "실제 제품 위치를 확인했습니다" CheckBox
6. 복구 사유 입력
7. DATA ONLY 이동 버튼
8. 최종 확인 MessageDialog

Source나 Destination이 변경되면 확인 CheckBox와 Preview를 초기화한다.
Timer Refresh 중 선택한 Material ID 또는 revision이 바뀌면 적용을 차단한다.

======================================================================
6. 허용 경로
======================================================================

인접한 위치 이동만 허용한다.

INPUT:

- InputCassette -> InputFeeder
- InputFeeder -> InputCassette
- InputFeeder -> InputStage
- InputStage -> InputFeeder

OUTPUT:

- OutputCassette -> OutputFeeder
- OutputFeeder -> OutputCassette
- OutputFeeder -> OutputStageGood
- OutputStageGood -> OutputFeeder
- OutputFeeder -> OutputStageNg
- OutputStageNg -> OutputFeeder

다음 경로는 금지한다.

- Cassette -> Stage 직접 이동
- Stage -> Cassette 직접 이동
- Input 계통 -> Output 계통
- Output 계통 -> Input 계통
- GOOD Bin -> NG Stage/NG Cassette
- NG Bin -> GOOD Stage/GOOD Cassette
- 동일 위치로 이동
- Unknown 위치로 이동
- 임의 Cassette/slot으로 반환

Cassette 반환은 원본 또는 사전에 예약된 정확한 Role/Slot만 허용한다.

======================================================================
7. Material 상태 전이
======================================================================

정상 물리 시퀀스의 상태 전이를 기본으로 한다.

- Cassette -> Feeder: WorkReady
- Feeder -> Stage: Working
- Stage -> Feeder: WorkReady

Feeder -> Cassette는 다음 두 Intent를 명시적으로 구분한다.

1) CANCEL RETURN

- Cassette에서 꺼낸 뒤 공정에 투입하지 않고 반환
- 상태: Ready

2) PROCESS COMPLETE RETURN

- Stage 작업 완료 후 반환
- 상태: Finish

UI에서 임의의 WaferMaterialState enum을 직접 선택하게 하지 않는다.
위 두 의미 있는 Intent 중 하나만 선택하게 한다.

Source의 공정 이력으로 Intent를 확정할 근거가 충분하면 자동 제안할 수 있지만,
근거가 불충분하면 사용자가 반드시 선택하고 확인해야 한다.

======================================================================
8. 안전 진입 조건
======================================================================

DATA RECOVERY 적용 전에 다음을 모두 검사한다.

- Controller가 존재한다.
- Machine/Unit이 존재한다.
- AutoRunning이 아니다.
- IsSequenceRunning이 false다.
- IsManualBusy가 false다.
- Initializing 또는 ManualRunning 상태가 아니다.
- 진행 중 Motion/Sequence scope가 없다.
- Source Material ID와 CurrentLocation이 Preview 시점과 같다.
- Source Material state/revision이 Preview 시점과 같다.
- Destination에 다른 Material이 없다.
- Source와 Destination은 허용된 인접 경로다.
- Cassette가 enabled/present/mapped 상태다.
- Cassette slot의 HasWafer/WaferId가 일치한다.
- GOOD/NG side와 OutputGrade가 일치한다.
- 원본/예약 Cassette Role과 Slot이 일치한다.
- 필요한 센서가 읽기 가능한 상태다.

실장비에서 센서가 UNKNOWN이거나 입력 읽기에 실패하면 적용을 차단한다.

Simulation/DryRun에서는 데이터 기반 가상 상태를 사용할 수 있지만,
화면과 로그에 Simulation 근거임을 명시한다.
Simulation 성공을 실제 설비 안전 검증으로 보고하지 않는다.

======================================================================
9. 센서 정합 계약
======================================================================

데이터 이동 전에 실물 위치를 가능한 범위에서 검증한다.

- Cassette -> Feeder:
  - Feeder Ring 감지 ON
  - Destination Feeder data empty
  - 선택 Cassette/slot과 Source Material 일치

- Feeder -> Stage:
  - Feeder Ring 감지 OFF
  - Stage Ring 감지 ON
  - Stage data empty

- Stage -> Feeder:
  - Stage Ring 감지 OFF
  - Feeder Ring 감지 ON
  - Feeder data empty

- Feeder -> Cassette:
  - Feeder Ring 감지 OFF
  - 대상 Cassette/slot data가 비어 있거나 동일 Material 복구 상태
  - 원본/예약 Role 및 Slot 일치

Cassette slot의 실시간 실물 감지가 불가능한 구조라면
Mapping 결과를 실시간 센서 증명으로 과장하지 않는다.
화면에 "CST PHYSICAL UNVERIFIED"를 표시하고 Maintenance 재확인을 요구한다.

10. Domain Service 계약
======================================================================

신규 전용 Service를 추가한다.

권장 파일:

QMC.CDT-320\Equipment\Materials\ManualMaterialRecoveryService.cs

권장 Request 정보:

- RequestId
- MaterialId
- ExpectedSource
- Destination
- ExpectedState
- ExpectedUpdatedAt 또는 revision
- TransferIntent
- Operator
- Reason
- Simulation 여부
- Sensor proof snapshot

권장 Result 정보:

- Success
- AlarmCode
- Message
- Before location/state
- After location/state
- Persistence result
- RecoveryRequired 여부

Service는 다음 순서를 한 흐름으로 처리한다.

1. Controller/권한/실행 상태 확인
2. Source와 Destination 재조회
3. 센서 Snapshot 취득
4. 허용 경로/side/slot/점유 검증
5. Material 변경을 lock 안에서 원자적으로 적용
6. Cassette slot과 Material location/state 동시 갱신
7. Runtime Projection 동기화
8. 변경 후 불변식 재검사
9. Snapshot 즉시 저장/flush
10. Audit Log 기록

UI가 MaterialStorage.State를 직접 변경하지 않는다.
UI가 Unit CurrentWaferMaterial 또는 MaterialState를 직접 변경하지 않는다.

======================================================================
11. Runtime Projection 동기화
======================================================================

INPUT:

- InputFeeder 목적지:
  - InputFeederUnit.SetCurrentWaferMaterial()
  - InputStageUnit cache는 비움

- InputStage 목적지:
  - InputStageUnit.SetCurrentWaferMaterial()
  - InputFeederUnit cache는 비움
  - 이전 active input map의 stale 표시/재사용을 방지
  - 동일 wafer의 유효 Mapping 복원 여부는 기존 정책을 사용

- InputStage 이탈:
  - active map/cache 정리
  - 진행 중 Die reservation/Permission이 있으면 임의 삭제하지 않는다.
  - 기존 해제 API로 안전하게 정리하거나 복구를 차단한다.

OUTPUT:

- OutputFeeder 목적지:
  - OutputFeederUnit MaterialState를 Occupied로 동기화

- OutputFeeder 이탈:
  - OutputFeederUnit MaterialState를 Empty로 동기화

- OutputStage 목적지:
  - 정확한 Good/Ng CurrentLocation 사용
  - 빈 Bin 공급이면 기존 OutputStage receive plan 초기화 규칙을 재사용
  - 기존 진행 Bin을 복구하는 경우 receive plan을 재생성하여 덮어쓰지 않는다.

SignalBus/Resume 상태가 실제 실행에 사용된다면
기존 중앙 정상화 API를 재사용한다.
새 UI가 독립적인 가짜 SignalBus 상태를 만들지 않는다.

======================================================================
12. 저장과 실패 처리
======================================================================

변경 후 MaterialStateService.NotifyAndSave()만 호출하고 즉시 성공으로 표시하지 않는다.

수동 복구는 다음을 수행한다.

- ManualMaterialRecovery 사유로 NotifyAndSave
- TryFlushPendingSave로 즉시 저장 완료 확인
- 저장 후 Material snapshot의 source/destination 재검증

MaterialSnapshotStore의 기존 temp -> 검증 -> replace/backup 구조를 유지한다.

저장 실패 시:

- 성공 메시지를 표시하지 않는다.
- Alarm/Event Log를 남긴다.
- RecoveryRequired를 설정한다.
- Auto 시작/재개를 차단한다.
- 물리 실물을 데이터 실패에 맞춰 되돌렸다고 가정하지 않는다.
- 저장 또는 재복구가 완료될 때까지 화면에 불일치 상태를 유지한다.

15. 구현 순서
======================================================================

1. 현재 호출 흐름, 모델, 센서, 캐시를 읽기 전용으로 재검증한다.
2. 구현 전 결정 항목을 사용자에게 보고하고 승인을 기다린다.
3. 데이터 Request/Result와 Domain Service 계약을 먼저 구현한다.
4. 허용 경로와 상태 전이 검증을 구현한다.

16. 구현 전 반드시 사용자에게 확인할 결정
======================================================================

- 신규 기능이 실제 모션 없이 Material 데이터만 복구하는 기능인지
- 적용 권한을 Maintenance 이상으로 할지
- Feeder -> Cassette의 Ready/Finish 선택 규칙
- Cassette 실물 확인이 불가능할 때 Maintenance 확인으로 허용할지
- Sensor UNKNOWN이면 무조건 차단할지
- InputStage 이탈 시 진행 중 Die reservation/Permission 처리
- OutputStage의 기존 receive plan이 있는 Bin 복구 정책
- Simulation에서 DATA RECOVERY를 허용할지
- CST STATUS에 복구 페이지 진입 버튼을 추가할지

위 결정 없이 물리 조건이나 Auto 재개 정책을 추측하여 구현하지 않는다.
