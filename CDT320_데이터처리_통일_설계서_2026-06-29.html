CDT-320 비전 / 작업뷰 데이터 처리 통일 설계서

목표: 비전 각 모듈(Wafer / Bottom / Side / Bin)과 작업뷰가 데이터를 한 가지 방식으로 처리하게 한다. 시뮬레이션과 실제 동작이 동일한 데이터 경로를 타도록 보장한다. · 2026-06-29
한 줄 요약. 지금은 스토어가 6개로 쪼개져 있고, 측정값이 두 가지 모델(BottomInspectionResult vs InspectionResultStore.Item)로 중복되며, 무엇보다 시뮬 경로가 결과 스토어를 거치지 않아 작업뷰에 안 뜬다. 이를 「공유 DTO → 단일 스토어 → 단일 진입점 → 이벤트 통일」 4단계로 정리한다.

1. 현재 상태 진단

1-1. 스토어가 6개로 분산

스토어역할읽는 뷰문제
InspectionResultStoreBottom/Side/Bin 결과 + 이력InspectionViewerControlSSOT에 가장 근접
WaferVisionResultStore웨이퍼 정렬/다이체크(핸들러측)위 스토어와 동기 안 됨 (별도 SSOT)
ModuleResultStore모듈별 OK/NG 판정 + 마크OperationPageInspectionResultStore와 역할 중복
MatchOverlayStore매치 마커OperationPage별도 폴링
ChartLimitStore / UnitContext차트 한계/단위뷰어보조 — 통합 대상 아님

1-2. 같은 측정값이 두 개의 다른 모델로 존재

핸들러 측 BottomInspectionResult
Width // double 프로퍼티 Height ChippingLeft / Right / Top / Bottom ForignMaxSize NgCode

타입 프로퍼티. Clone() / UpdateFrom() 수기 복제.

비전 측 InspectionResultStore.Item
Values["Width"] // Dictionary<string,double> Values["Height"] Values["Max Chipping Depth"] Pass / Channel / IndexX,Y / Image

문자열 키 딕셔너리. 두 모델 사이 수기 변환 필요.

Side는 더 심함. 비전은 4채널(Front ch0/1, Back ch2/3)을 지원하지만, 핸들러 SideInspectionResult는 ChippingDepth 하나뿐이다. 두 앱이 사실상 다른 데이터를 본다.

1-3. 업데이트 방식이 뷰마다 제각각

뷰데이터 출처받는 방식
InspectionViewerControlInspectionResultStore이벤트 푸시 Changed 구독
OperationPage (프레임)IVisionModule폴링 250ms ViewerFrameSeq
OperationPage (판정)ModuleResultStore폴링 직접 읽기
WorkMainPageMaterialSnapshot폴링 500ms 타이머

2. 핵심 문제 — 시뮬 ≠ 실제

코드 확인 결과 InspectionResultStore.Record()가 호출되는 곳은 단 두 군데다.

  • VisionCommandCore.cs:226 — 실제/Sim 공유 검사 실행 경로
  • InspectionViewerControl.cs:553 — 뷰어 수동 테스트

그런데 핸들러 측 자동 시퀀스의 시뮬 단축 경로는 이 스토어를 거치지 않는다.

실제 경로 (정상)
TCP INSPECT → VisionCommandCore.InspectOnImage() → InspectionResultStore.Record() ✔ → Changed 이벤트 → 작업뷰 갱신 ✔
시뮬 경로 (누락)
PickerBottomInspectionSequence → IsVisionBypassed() == true → SimulateBottomResult() // 합성 PASS → MaterialStateService 직접 기록 ✘ InspectionResultStore 안 거침 ✘ 작업뷰에 안 뜸

결론. 시뮬에서는 검사 결과가 작업뷰까지 도달하지 않는다. SimulateBottomResult() / SimulateSideResult()가 InspectionResultStore를 우회하기 때문. 이 분기를 없애는 것이 「시뮬=실제」의 핵심이다.

3. 통일 아키텍처

대원칙 — 동작은 따로, 데이터는 통일. Bottom/Side/Bin은 각자의 모듈 요청으로 독립 실행한다(통일 대상 아님). 통일하는 것은 결과를 담고·저장하고·표시하는 방식뿐이다. 각 모듈은 VisionResult.Mode 태그로 자신을 구분하며, 스토어는 모드별 칸으로 분리 보관하므로 모듈 독립성은 그대로 유지된다. 향후 "모듈별 분리 관리" 요청이 와도 이 구조에서 모드별로 분기 가능하다.

원칙: 「공유 DTO 하나 → 단일 스토어 하나 → 단일 진입점 하나 → 이벤트 구독 하나」. 시뮬이든 실제든 반드시 같은 진입점을 통과시켜 항상 스토어가 채워지게 한다.

[실제] TCP INSPECT ─┐ ├─→ IVisionResultSink.Publish(VisionResult) [시뮬] SimInspect ──┘ │ ├─→ InspectionResultStore.Record() (항상) ├─→ MaterialStateService (항상) └─→ Changed 이벤트 │ 작업뷰 전부 ◀── Changed 구독 (폴링 제거)
레이어통일안
① 공유 DTOQMC.Common에 VisionResult 단일 모델 신설. Bottom/Side(4채널)/Bin/Wafer를 모두 표현. 핸들러 BottomInspectionResult·비전 Item은 이 DTO로 통일하거나 어댑터 변환만 허용.
② 단일 스토어InspectionResultStore를 결과 허브로 승격. ModuleResultStore의 OK/NG·마크 역할을 흡수(또는 내부 위임). Wafer도 같은 스토어의 한 모드로 편입.
③ 단일 진입점IVisionResultSink.Publish() 신설. 실제 TCP 수신부와 시뮬 모두 이 한 메소드를 호출. SimulateXxxResult()는 결과를 만든 뒤 반드시 Publish로 흘려보낸다(우회 금지).
④ 이벤트 통일모든 작업뷰가 Changed 이벤트를 구독. 250/500/1500ms 폴링 타이머 제거(프레임 표시 등 불가피한 것만 유지).

5. 「시뮬 = 실제」 보장 규칙 (고정)

  • R1. 검사 결과는 시뮬·실제·DryRun 무관하게 오직 IVisionResultSink.Publish() 한 경로로만 스토어에 들어온다.
  • R2. SimulateXxxResult()는 값만 만들고 끝내지 않는다 — 반드시 Publish로 흘려보낸다.
  • R3. 작업뷰는 결과를 직접 파싱하거나 폴링하지 않는다 — Changed 이벤트만 구독한다.
  • R4. 측정값 모델은 VisionResult 하나. 뷰별 전용 DTO 신설 금지(어댑터 변환만 허용).
  • R5. (AGENTS.md) 이동 완료 확인 등 시퀀스 안전규칙은 시뮬에서도 생략하지 않는다.

7. 추천 시작 지점

Phase 1 + Phase 2를 먼저 적용하기를 권한다. 신규 파일 추가 + 시뮬 Publish 연결만으로 위험이 낮고, 「시뮬에서 작업뷰에 결과가 안 뜬다」는 가장 큰 증상이 바로 해소된다. 스토어 통합(Phase 3)과 폴링 제거(Phase 4)는 그 다음 순차 진행한다.
